# 应急手册（EMERGENCY）

## 第一原则

**先停止下单，再排查原因。** 任何不确定情况下，默认动作是停用策略并撤掉未成交委托，而不是「再等一根 bar 看看」。

## 一键停用（Kill Switch）

执行层开关集中在 `execution/qmt/live_config.py`：

```python
KILL_SWITCH = True      # True = 策略立即停止且不再发任何委托
DRY_RUN = True          # True = 只记录意图，不调用任何下单接口
MODE = "semi_auto"      # semi_auto 只出信号 / full_auto 才自动下单
```

运行时也可在 QMT 里调用 `strategy.set_kill_switch(C, True, "原因")`，会同步断开订单管理器并写审计。

操作顺序：
1. 在 QMT 客户端停止策略运行（界面操作优先，最快且不受代码状态影响）。
2. 撤掉全部未成交委托。
3. 将 `KILL_SWITCH` 置回 `True`（必要时把 `DRY_RUN` 也置回 `True`）并保留现场日志。
4. 导出成交/持仓/资金，与本地信号账本对账。
5. 记录事件时间线、触发条件、处置动作、影响范围。

## 自动熔断条件

| 触发 | 动作 |
|---|---|
| 当日亏损触及 `risk.max_daily_loss_pct` | 停止新开仓 + 撤未成交单 |
| 行情断流 / 快照时间戳停滞 | 停止策略 + 撤单 |
| 开盘前或收盘后对账不一致 | 停止策略，禁止新委托 |
| 报撤频率异常 / 委托笔数超 `max_daily_orders` | 停止策略 |
| 客户端版本变化 / 接口返回结构异常 | 停止策略 |
| 订单超时未回报 / 状态进入 `unknown` | 主动查询并撤单，禁止重复报单 |
| 断网、断电、客户端崩溃 | 恢复后先对账，确认无幽灵单再启动 |

## 分类处置

- **重复报单**：以 `client_order_id` 去重；核对券商实际委托，勿重复撤单。
- **部分成交**：按实际成交量更新持仓与账本，剩余按撤单处理。
- **漏单 / 错单**：立刻停用；以券商成交回报为准，不补单、不追单，先对账。
- **数据异常**：校验 `source` / `as_of` / `adjust`；缺失字段一律拦截而不是按 0 处理。
- **规则被误改**：回滚到上一版本规则文件与沙箱副本，哈希核对后重启。

## 禁止的应急动作

- 不要为了「补回」信号而临时绕过风控校验
- 不要在未对账前重发委托
- 不要用任何外部进程 / 文件 / 网络去「指挥」沙箱内策略
- 不要在虚拟机、云桌面或他人机器上恢复运行

## 恢复流程

1. 对账零差异 → 2. 回归测试全绿 → 3. 以半自动（人工逐笔确认）重启 → 4. 观察 N 个交易日 → 5. 才考虑恢复全自动。
2. 恢复后如策略、软件、报单速率或资金规模发生变化，按合规要求做变更报告。
